Agent Harness(the loop):

An agent harness is the control loop around an LLM that keeps the whole agent running:
send prompt → get model output → detect tool calls → execute tools → feed results back → repeat until the model says it’s done.

Verified: **mostly correct**, with two important wording changes.

1. **The architecture claim is sound, but “much better” is not directly proven for this exact pair.**
   GLM-4.7-Flash is the right component for generation/agent work, while BGE-Code-v1 is the right component for retrieval. That split is well supported. But I did **not** find a direct benchmark proving `glm-4.7-flash:q4_K_M + BAAI/bge-code-v1` beats GLM alone on your exact agentic coding/RAG workload. Treat “much better” as a strong engineering inference, not a sourced benchmark result.

2. **GLM-4.7-Flash details check out.**
   The official model card says GLM-4.7-Flash is a **30B-A3B MoE** model and reports the exact benchmark numbers you quoted: **SWE-bench Verified 59.2, τ²-Bench 79.5, BrowseComp 42.8**. The Ollama `q4_K_M` page lists **29.9B parameters**, **Q4_K_M**, and **19GB**. ([Hugging Face][1])

3. **BGE-Code-v1 details check out.**
   Official BGE docs describe `BAAI/bge-code-v1` as an LLM-based **code embedding** model for code/text/multilingual retrieval, list it as **multilingual, 1.5B, 6.18GB**, and call it code-retrieval-focused. The Hugging Face repo is tagged for embedding/feature extraction, not chat. ([bge-model.com][2])

4. **The RTX 3090 caveat is correct, and maybe understated.**
   NVIDIA lists the RTX 3090 with **24GB GDDR6X**. With GLM Q4_K_M at about **19GB**, plus BGE-Code-v1 runtime memory, plus KV cache, CUDA overhead, allocator fragmentation, and long context, keeping both GPU-resident is very likely to be fragile. The “BGE fp16 ~3+GB” estimate is mathematically plausible from 1.5B parameters, but the published HF repository size is about **6.19GB**, so the actual residency depends on dtype/loading path. ([NVIDIA][3])

5. **The FAISS recommendation is correct.**
   FAISS is appropriate for local dense-vector retrieval, and the “normalized cosine/IP” advice matches the FAISS wiki: for cosine similarity, use `METRIC_INNER_PRODUCT` and normalize both database and query vectors. ([GitHub][4])

6. **The optional reranker advice is reasonable.**
   FlagEmbedding’s own README says BGE rerankers are more accurate but less efficient, and recommends reranking top-k documents returned by embedding models. Top-20 → top-5 is a normal practical pattern, though the exact k values are workload-dependent. ([GitHub][5])

7. **The Ollama tool-use warning is supported, but should be phrased historically.**
   A GitHub issue reported GLM-4.7-Flash via Ollama stopping after tool calls in OpenCode while the same model via vLLM worked; that issue is now **closed**. Another Ollama issue about GLM-4.7-Flash tool parsing remains **open** in the view I found. So “Ollama has had GLM-4.7 tool-call handling issues” is accurate; “Ollama is currently broken” would be too strong. ([GitHub][6])

8. **The vLLM/SGLang parser flags are verified.**
   The official GLM-4.7-Flash card shows vLLM/SGLang serving examples using `--tool-call-parser glm47`, `--reasoning-parser glm45`, and `--enable-auto-tool-choice` for vLLM. ([Hugging Face][1])

9. **The community Modelfile fix is real, but not official for all setups.**
   The Unsloth HF discussion includes a pinned community Modelfile using `RENDERER glm-4.7` and `PARSER glm-4.7`, claiming working tool calls with Cline/Roo/Kilo. Good to mention, but label it as community guidance, not an upstream guarantee. ([Hugging Face][7])

10. **The smaller-embedder alternatives exist.**
    `jinaai/jina-code-embeddings-0.5b` is a code retrieval embedding model built on Qwen2.5-Coder-0.5B, and Qwen3-Embedding has a 0.6B model intended for embedding/ranking with code retrieval among its tasks. ([Hugging Face][8])

**Suggested corrected bottom line:**

> Yes, `glm-4.7-flash:q4_K_M + BAAI/bge-code-v1` is a well-matched local agentic coding/RAG architecture: GLM handles planning, code editing, reasoning, and tool calls; BGE-Code-v1 handles repository retrieval and context selection. This is likely better than GLM-only prompting when repo context matters, but the exact “much better” claim should be benchmarked on your tasks. On a single RTX 3090, keep GLM on GPU and avoid keeping BGE-Code-v1 permanently GPU-resident unless you have measured enough VRAM headroom. For reliable agent tool use, the serving stack and GLM-specific tool/reasoning parsers matter as much as the model itself.
